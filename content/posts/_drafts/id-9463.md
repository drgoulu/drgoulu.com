Notre prof de bases de données à l'EPFL nous avait dit "Bon, comme toute l'industrie utilise encore un vieux truc qui s'appelle [SQL](https://fr.wikipedia.org/wiki/Structured_Query_Language), il faut bien passer un cours ou deux là dessus, mais on va surtout parler de l'avenir : les [bases de données orientée objet](https://fr.wikipedia.org/wiki/base_de_données_orientée_objet)." 30 ans plus tard, les bases de données objet ont dû apprendre à parler SQL, et les bases [NoSQL](https://fr.wikipedia.org/wiki/NoSQL) ne sont pas près de détrôner le "vieux truc". ## Pirates et logique

Au moment où j'écrivais mes premières requêtes SQL, Annick travaillait le problème de logique ci-dessous avec une de ses élèves :

{{< figure src="images/nYCs2q4QTmL3m6mvagrMUcc4ieQ.jpg" alt="(image : Maïkresse d'appui)" caption="(image : Maïkresse d'appui)" link="http://kilop.eklablog.com/prolongement-si-j-etais-un-pirate-a113031390" align="aligncenter" width="1063" >}}

SQL permet de le résoudre très failement. Il faut d'abord créer et remplir une table de pirates avec des "champs" contenant leurs attributs vestimentaires \[expand title="(cliquer pour voir)"\]

\[code lang="sql"\] -- on crée une table avec les attributs des pirates CREATE TABLE pirate ( id BIGSERIAL NOT NULL, chemise CHAR(10) NOT NULL, bandeau BOOLEAN NOT NULL, pantalon CHAR(10) NOT NULL, PRIMARY KEY(id) );

\-- on ajoute les pirates dans la table INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (1, 'vert', false, 'rayure'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (3, 'rouge', true, 'rayure'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (2, 'bleu', false, 'pois'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (4, 'bleu', false, 'rayure'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (5, 'rouge', true, 'carreau'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (6, 'rouge', false, 'carreau'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (7, 'rouge', false, 'rayure'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (8, 'bleu', true, 'rayure'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (9, 'jaune', true, 'pois'); INSERT INTO pirate (id, chemise, bandeau, pantalon) VALUES (10, 'bleu', false, 'carreau'); \[/code\]

\[/expand\] puis on cherche les pirates correspondant au problème posé avec une requête SELECT:

\[code lang="sql"\] SELECT \* FROM pirate WHERE pantalon !='rayure' AND NOT bandeau AND chemise !='bleu'; \[/code\]

qui donne  : 6, rouge, false, carreau

Comme on le voit, SQL est un langage de programmation "[déclaratif"](https://fr.wikipedia.org/wiki/programmation_déclarative) où l'on décrit logiquement le résultat attendu, sans spécifier la séquence des opérations à effectuer pour l'obtenir comme dans les langages de programmation "[impératifs](https://fr.wikipedia.org/wiki/programmation_impérative)" classiques.

## Plans d'exécution

Il existe de nombreuses manières de résoudre ce genre de problème, par exemple:

1. entourer l'ensemble de ceux qui n'ont pas de pantalons à rayures (2,5,6,9,10), entourer le sous-ensemble de ceux qui n'ont pas de bandeau (2,6,10), puis dans ce sous-ensemble ceux qui ont une chemise qui n'est pas bleue : il n'y a que le 6.
2. tracer tous ceux qui ont un pantalon à rayure (1,3,4,7,8), puis ceux qui ont un bandeau (3,5,8,9), puis ceux qui ont une chemise bleue (2,4,8,10) : reste le 6
3. examiner les pirates l'un après l'autre, vérifier les 3 conditions l'une après l'autre : seul le 6 les satisfait toutes

## Pourquoi je hais quand même SQL
